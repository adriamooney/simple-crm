# Simple CRM

A lightweight, single-tenant CRM that lives on top of a **Google Sheet**. It reads your
contacts from the sheet, scans **Gmail** for each contact's latest conversation, uses
**Claude** to derive a stage/sentiment/summary/next-step, and writes that context back into
the sheet. A web dashboard renders the sheet as a searchable, filterable table.

It runs entirely on **Vercel** (Next.js serverless functions + a scheduled cron). There is no
database to operate and nothing that needs a machine of yours to stay on — the Google Sheet is
the data store.

---

## What it does

- **Contact table UI** backed by a Google Sheet — search across name/email/phone/website/
  company/summary/snippet, plus column filters for stage and company, and a per-contact detail
  modal.
- **Gmail enrichment** — for each contact, finds the most recent inbound/outbound messages
  across up to two connected Gmail inboxes.
- **AI summarization** — Claude turns the latest thread snippet into `stage`, `sentiment`,
  `summary`, and `nextFollowUp`.
- **Two ways to sync** — a **daily cron** (background) and a **"Sync Now"** button (on demand).
- **OAuth connect flow** — connect Gmail + Sheets from `/settings`; refresh tokens are stored in
  Vercel KV, so no manual token juggling.

## How it works

```
                 ┌─────────────────────────── Vercel ───────────────────────────┐
 Browser  ─────► │  /            Dashboard (client component)                    │
                 │  /settings    Connect/reconnect Google accounts               │
                 │                                                               │
                 │  GET  /api/contacts        read sheet → contacts JSON         │
 "Sync Now" ───► │  POST /api/sync/manual     enrich + write back               │
 Daily cron ───► │  GET  /api/sync            enrich + write back (CRON_SECRET)  │
                 │  /api/oauth/google/*       OAuth start / callback / status    │
                 └───────────────────────────────────────────────────────────────┘
                        │                 │                     │
                        ▼                 ▼                     ▼
                  Google Sheets       Gmail API             Claude API
                  (contacts store)    (thread scan)         (summaries)
                        ▲
                        └──── refresh tokens ──── Vercel KV (slots 1 & 2)
```

**Sync pipeline** (`syncCrmFromGmail` in `src/lib/crm.ts`):

1. Read all contacts from the sheet (`getContacts`).
2. For each contact, query Gmail (`to:<email> OR from:<email>`) across both connected slots and
   collect the most recent messages.
3. Derive timing — last outbound, last inbound, days since response.
4. Ask Claude to summarize the latest snippet into stage/sentiment/summary/next-step.
5. Write the enriched row back to the sheet.

**Auth** is Google OAuth. Connecting an account at `/settings` stores its refresh token in Vercel
KV under a slot (1 or 2). Sheets reads/writes use slot 1; Gmail scanning uses both slots. When a
refresh token goes bad (Google returns `invalid_grant`), the app raises a typed
`ReconnectRequiredError` (`src/lib/errors.ts`), the API routes return `401 { reconnect, slot }`
instead of a raw 500, and the dashboard shows a **"Reconnect"** banner pointing at `/settings`.

## What it produces

The system of record is the Google Sheet. Each sync (re)writes these 15 columns per contact row
(`src/types/crm.ts`):

`name | email | phone | website | company | stage | lastOutbound | lastInbound | daysSinceResponse | sentiment | summary | nextFollowUp | threadId | snippet | updatedAt`

- `name / email / phone / website / company` — inputs you maintain in the sheet.
- `stage / sentiment / summary / nextFollowUp` — generated by Claude.
- `lastOutbound / lastInbound / daysSinceResponse / threadId / snippet` — derived from Gmail.
- `updatedAt` — timestamp of the last sync for that row.

The API also returns contacts as JSON at `GET /api/contacts`.

- `src/app/api/contacts/route.ts` — `GET` contacts from the sheet.
- `src/app/api/sync/route.ts` — cron entry point; `GET`, authorized by `CRON_SECRET` bearer token.

- `src/app/api/oauth/google/start/route.ts` — begins the OAuth flow for a slot.
- `src/app/api/oauth/google/callback/route.ts` — exchanges the code and stores the refresh token.
- `src/app/api/oauth/google/status/route.ts` — which slots are connected (used by `/settings`).

**Library**
- `src/lib/crm.ts` — the sync orchestration (`syncCrmFromGmail`).
- `src/lib/google.ts` — Sheets/Gmail clients, `getContacts`, `updateContactRow`.
- `src/lib/google-oauth.ts` — OAuth client, signed `state`, callback handling.
- `src/lib/claude.ts` — `summarizeConversation` (Claude call + JSON parsing).
- `src/lib/token-store.ts` — refresh-token storage in Vercel KV.
- `src/lib/errors.ts` — `invalid_grant` detection and the `ReconnectRequiredError` type.
- `src/lib/env.ts` — typed environment-variable access.
- `src/types/crm.ts` — the `Contact` shape and sheet column order.

**Config**
- `vercel.json` — the daily cron (`0 8 * * *` → `/api/sync`).
- `.env.example` — environment variable template.

## Setup

### 1. Google Sheet

Create a tab (default name `contacts`) with these headers in row 1:

`name | email | phone | website | company | stage | lastOutbound | lastInbound | daysSinceResponse | sentiment | summary | nextFollowUp | threadId | snippet | updatedAt`

You only need to fill in the left-hand input columns (name, email, etc.); the rest are populated
by sync. If your tab isn't named `contacts`, set `GOOGLE_SHEET_TAB`.

### 2. Environment variables

Copy the template and fill it in:

```bash
cp .env.example .env.local
```

Required:

- `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` — OAuth client (Google Cloud Console).
- `GOOGLE_SHEET_ID` — the sheet that holds contacts.
- `GOOGLE_SHEET_TAB` — optional; defaults to `contacts`.
- `APP_URL` — base URL of the app (`http://localhost:3000` locally, the Vercel URL in prod). Used
  to build the OAuth redirect URI.
- `OAUTH_STATE_SECRET` — random string; signs the OAuth `state` parameter.
- `ANTHROPIC_API_KEY` — Claude API key.
- `ANTHROPIC_MODEL` — optional; defaults to `claude-sonnet-4-6`.
- `CRON_SECRET` — bearer token the cron must present to `/api/sync`.
- Vercel KV vars (`KV_REST_API_URL`, `KV_REST_API_TOKEN`, …) — provisioned automatically when a KV
  store is attached to the Vercel project.

Optional legacy path (skip if you use the `/settings` OAuth flow):
`GMAIL_ACCOUNT_1_EMAIL` / `GMAIL_ACCOUNT_1_REFRESH_TOKEN` (and `…_2_…`).

### 3. Google Cloud Console

- Enable the **Gmail API** and **Google Sheets API**.
- Add the OAuth redirect URI: `<APP_URL>/api/oauth/google/callback`.
- **Publish the OAuth consent screen** (move it out of "Testing"). In Testing mode Google expires
  refresh tokens after ~7 days, which surfaces as `invalid_grant` and forces a weekly reconnect.

## Running locally

```bash
npm install
npm run dev
```

Open `http://localhost:3000`, go to **/settings**, and click **Connect** for slot 1 (and slot 2 if
you scan a second inbox). Then use **Sync Now** on the dashboard.

To trigger the cron route by hand:

```bash
curl -H "Authorization: Bearer <CRON_SECRET>" http://localhost:3000/api/sync
```

## Deploying (Vercel)

- The project is a standard Next.js app; pushing to `main` deploys via the Git integration.
- Set every env var above in the Vercel project settings, and attach a KV store.
- `vercel.json` registers the daily cron (`0 8 * * *`). Set the same `CRON_SECRET` in Vercel.
- **Cron cadence depends on plan:** the Hobby plan effectively runs crons about once per day; Pro
  runs sub-daily schedules reliably.

## Scaling caveats (this is an MVP)

The current design is deliberately simple — one sheet, one user, synchronous sync. To grow beyond
a personal tool, expect to address:

- **The Google Sheet is the database.** Fine for hundreds of rows; it becomes the bottleneck at
  scale (row-level rewrites, no real querying, no relations, easy to corrupt by hand editing). A
  real datastore (Postgres/Neon via the Vercel Marketplace) would be the first migration.
- **Sync is synchronous and O(contacts).** `syncCrmFromGmail` loops contacts one at a time, each
  doing ~20 Gmail calls + 1 Claude call + 1 sheet write. With `maxDuration = 300s`, a large list
  will time out. Scaling means batching/queuing (e.g. Vercel Queues) and processing incrementally
  rather than "all contacts in one request."
- **Single-tenant / two fixed inboxes.** Accounts are hard-coded to slots 1 and 2 in KV. Multi-user
  or multi-inbox support needs per-user auth (NextAuth is a dependency but not wired into the app)
  and per-user token namespacing.
- **No incremental sync.** Every run re-scans and re-summarizes every contact from scratch. Gmail
  `historyId`/watch push notifications and change detection would cut cost dramatically and enable
  near-real-time updates.
- **Cost / rate limits.** One Claude call per contact per run adds up; Gmail and Sheets both have
  quotas. Caching summaries, only re-summarizing changed threads, and de-duping API calls matter as
  volume grows.
- **No tests and thin error handling.** There's no test suite, and failures beyond `invalid_grant`
  (Gmail quota, Sheets 5xx, Claude parse failures) are only partially handled. Retries, structured
  logging/alerting, and coverage of the sync pipeline would be needed for reliability.
- **Auth surface.** `/api/contacts` and `/api/sync/manual` are unauthenticated — anyone who can
  reach the deployment can read contacts and trigger a sync. A real deployment needs app-level auth
  in front of the UI and the manual endpoints.
- **Claude output is trusted.** Summaries are parsed from model JSON with a best-effort fallback;
  robust schema validation (e.g. tool/structured outputs) would harden this.
